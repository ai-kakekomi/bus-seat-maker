## 3. 残課題：席未定 35件

### 3.1 件数の動き

| 時点 | 席未定（組・日） | 中身 |
|---|---|---|
| #2 だけ | 167（150日） | かたちを一覧だけにし、押し込みをやめた |
| #2 終了時点（探索あり） | 11 | 敷き詰めの探索（仕様書にない処理）を足していた |
| #2 ＋ 最後部の列の条件 | 79 | 探索を外し、最後部の列を開く条件を直した |
| #2 ＋ 最後部の列の条件 ＋ #4 | 37 | 3段の置き方 |
| **最終**（＋相席の当番） | **35** | |

**#2 終了時点（11件）より増えているのは、敷き詰めの探索を外したため。** 探索は仕様書（docs/アルゴリズム.md）にない処理で、#4 を入れてから必要かどうかを判断する、という方針で外した。探索を戻せば減るが、ほぼ満席の見本が約10秒になる（上限8秒を超える）。

### 3.2 35件の内訳

| 見方 | 内訳 |
|---|---|
| 構成 | **ふだん（2名が大半）0件**／意地悪（いろいろな人数）35件 |
| 空席の数 | 空席0：27件／空席1：4件／空席2：4件／空席4・8：0件 |
| 席未定になった組 | 2名14・4名7・6名3（**偶数の組 24件**）／3名11（奇数の組 11件）／1人参加0／前席オプション組0 |
| 起きた申し込み | 300件のうち21件 |
| その日の空席の形 | 空席119席のうち、**2人掛けがまるごと空いている所は0**（1席ずつ散らばっている） |

### 3.3 原因

```
奇数の組（3・5・7名）は、置くと2人掛けの片方を1席残す
  → その1席を埋められるのは「1人参加」か「奇数の組どうしのかみ合わせ（設計書3.1、#3）」だけ
  → ぎゅうぎゅう（空席0〜2）で1人参加が足りないと、1席ずつの空きが散らばって残る
  → 2人掛けがまるごと空いている所がなくなり、偶数の組も3名の組も入れない → 誰かが席未定
  → 見直し（順番の入れ替え）は「席未定の人数」が少ないほうを選ぶので、
     6名の偶数の組と7名の奇数の組なら、6名の偶数の組を席未定にする
```

- 3段で偶数の組を先に置いても、見直しで順番が入れ替わり、偶数の組が最後に回されて席未定になる（偶数の組が席未定になった日は、すべて並べ順の3段が崩れていた）
- **「どうしても誰かが席未定になるとき、どの組を席未定にするか」が設計書に決まっていない**。今のコードは「席未定の人数が少ないほう」なので、#4 の考え（偶数を守る）と逆に、偶数の組が犠牲になりやすい

### 3.4 修正方針案（代表に決めていただきたいこと）

**(1) どの組を席未定にするか（N1）**

| 案 | 席未定にする順番 | 良い点 | 気になる点 |
|---|---|---|---|
| **P1 偶数を守る**（AI のおすすめ） | 1人参加 → 奇数の組（人数の少ない組から）→ 偶数の組。前席オプション組は最後まで守る | #4 の「偶数をバラバラにしない。奇数で調整」そのまま。3名の組なら、添乗員さんが鍵席・相席で手直ししやすい | 席未定の**人数**は増えることがある（6名の偶数の組の代わりに、3名の組2組） |
| P2 申し込みの遅い組から | 偶数・奇数は問わず、申し込み順の遅い組から | 分かりやすく、お客様に説明しやすい | 偶数の組も席未定になる |
| P3 人数の少ない組から | 手で入れる席の少ない組から | 手で入れるときに空席を探しやすい | 2名の組が先に席未定になる |
| P4 P1 ＋ もう1段 | P1 の前に、奇数の組の最終手段のかたち（5名の4＋1 など）と最後部の真ん中を必ず試す | 添乗員さんが最後にやる工夫を先にやる | どこまで「必ず試す」かを決める必要がある |

決まったら、設計書 4.2（手順4）と 4.3（出来ばえの比べ方）に書き足してから、見直しの点数のつけ方を直す。

**(2) 35件をさらに減らすか（N2）**

| 案 | 中身 | 見込み | 関係 |
|---|---|---|---|
| A 今のまま | 席未定の枠で、添乗員さんが手で直す | 35件のまま（ふだんの構成では0件） | ― |
| B 奇数の組のかみ合わせ | 3名どうしを横3と鍵席でかみ合わせ、1席ずつの空きを減らす | 3名の組の分（11件）と、偶数の組の分も減る見込み | 設計書3.1。**#3 で実装** |
| C 左右の寄せ方 | 今は同じ列の中で左から詰めている。右に寄せる置き方も候補にする | 減る見込み（未測定） | 設計書2章「左右は区別しない」 |
| D 敷き詰めの探索を戻す | 仕様書に手順として書いてから入れる | 大きく減る（11件前後） | 遅くなる（約10秒）。仕様書に手順を足す必要 |

AI のおすすめの順番: (1) を P1 で決める → #3 で B → それでも多ければ C・D を検討。

**代表に伺いたいこと**

このリポジトリには、プルリクエストで自動でテストを動かす仕組み（GitHub Actions など）がない。PR の画面にテスト結果は出ないので、確かめるときは手元で動かす（Node.js が必要。外部パッケージは不要）。

```
node test/run.js       単体テスト（155件、約47秒）
node test/field.js     添乗員さんの入力（違反0件なら終了コード0）
node test/stress.js    大量テスト（300件、約160秒。違反の種類ごとの件数を出す）
```

目で確かめるときは、`debug.html`（大量テスト・添乗員さんの入力・かたちの一覧）を開く。
